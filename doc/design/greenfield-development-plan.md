# 从零开发计划（Greenfield）

> 本文件是 `doc/design-1.md` 的子系统文档之一，用于“删除旧项目、从零开始开发”的场景。
> 它与 `development-plan.md`（重构现有项目）是两种路线：**本文件是未来从零重建的主计划**，重构版保留为历史对照。
> 执行原则：先搭骨架、再逐步长出业务；每个里程碑可构建、可验证、可回滚。

---

## 0. 与重构版的关系

| 项目 | 重构版 `development-plan.md` | 从零版本文件 |
| --- | --- | --- |
| 前提 | 旧代码存在 | 旧代码不存在，或只作为行为参考 |
| 第一阶段 | 建立基线/拆分现有文件 | 搭建工程骨架与安全边界 |
| 核心工作 | 移动/拆分/整理 | 从空目录新建功能模块 |
| 风险 | 行为回归 | 行为差异（旧代码细节可能丢失） |
| 建议 | 保留旧代码做对照 | 保留旧项目副本/行为快照，或接受文档级对齐 |

## 1. 全局基础

### 1.1 必须已有的输入

- `doc/design-1.md`：总纲
- `doc/design/product-scope.md`：功能范围
- `doc/design/decisions.md`：已确认的产品/UX 决策
- `doc/design/architecture.md`：目标架构
- `doc/design/main-process.md`：主进程设计
- `doc/design/renderer-ui.md`：UI 设计
- `doc/design/shared-contracts.md`：共享契约
- `doc/api-research.md` + `api.config.example.json`：荒启 API 契约
- 旧项目行为快照（若可用）：README、截图、CHANGELOG、CDP 截图等

### 1.2 约束

- 技术栈：Electron 34 + React 19 + TypeScript + electron-vite + Zustand + better-sqlite3 + Milkdown + CodeMirror 6。
- 目录结构按 `architecture.md` 执行。
- 功能、产品、UX 决策以 `decisions.md` 为准。
- 每个里程碑结束必须：`npm run typecheck` + `npm run build` 通过。
- 从 M3 开始尽可能支持 `dev:test` 测试模式。

### 1.3 从零开发 vs 重构的验收差异

从零开发不要求“与旧代码逐行一致”，但要求“文档中定义的行为正确”。旧代码中未文档化的细节，需要在新开发过程中显式补充到 `decisions.md` / 行为文档中。

## 3. 里程碑详细计划

### M0 工程骨架

#### 目标
- 从空目录搭建可运行的 Electron 应用。

#### 任务
- [ ] 初始化 package.json，锁定 Electron 34 / React 19 / TypeScript / electron-vite。
- [ ] 创建 `src/main/`、`src/preload/`、`src/shared/`、`src/renderer/` 目录。
- [ ] 按 `architecture.md` 创建目标子目录（`main/bootstrap`、`main/ipc`、`main/services`、`main/adapters`、`main/infra`、`renderer/features`、`renderer/components`、`shared/contracts`、`shared/domain`）。
- [ ] 实现最小主进程：单实例锁、API 配置加载、窗口创建。
- [ ] 实现最小 preload：`window.hqsf` 空壳 + `ping` / `getAppInfo`。
- [ ] 实现最小渲染层：React 根组件 + 空壳页面。
- [ ] 配置 `electron-builder.yml`、`tsconfig.node.json`、`tsconfig.web.json`。

#### 验收标准
- [ ] `npm run dev` 可启动开发模式。
- [ ] `npm run typecheck` 通过。
- [ ] `npm run build` 通过。
- [ ] 窗口可显示，`window.hqsf.ping()` 可返回。

### M1 安全边界与 IPC 基础

#### 目标
- 建立所有后续功能依赖的安全与通信基座。

#### 任务
- [ ] 窗口：`contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`。
- [ ] 外链处理：`setWindowOpenHandler` deny + 系统浏览器打开。
- [ ] IPC：建立 `ok` / `fail` 返回约定，`senderFrame` 校验。
- [ ] 在 `shared/contracts/` 定义 IPC channel 与请求/响应类型。
- [ ] 建立 `main/ipc/` 分域 handler 文件（即使最初为空，也保留目录约定）。
- [ ] 建立 `main/infra/net/`：`apiRequest`、`endpoint`、`api.config` 加载与校验。
- [ ] 建立测试模式：`dev:test` 独立 userData。

#### 验收标准
- [ ] 渲染层无法访问 Node/ipcRenderer。
- [ ] 所有 IPC 返回 `{ok:true,data} | {ok:false,error}`。
- [ ] API 配置缺失/损坏时 fail-fast。
- [ ] `dev:test` 与正式模式隔离。

### M2 认证与协议

#### 目标
- 完成登录/会话/协议门闭环。

#### 任务

- [ ] `main/services/auth-service.ts`：登录、会话、退出、启动校验。
- [ ] `main/adapters/auth.adapter.ts`：账号密码接口。
- [ ] `main/ipc/auth.handlers.ts`。
- [ ] 渲染层 `features/auth/`：登录模态、首启协议门、用户协议。
- [ ] 决策：仅账号密码登录；单账号单会话。
- [ ] 启动默认进入推荐首页；已登录用户可通过用户卡进入用户页。

#### 验收标准
- [ ] token 不下发渲染层。
- [ ] 未登录可浏览/写作。
- [ ] 登录/退出/重启恢复会话。
- [ ] 协议门在首次启动/版本更新时出现。

## 4. 阶段依赖

```
M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 → M9 → M10
```

- M1 是安全/通信基座，必须先于业务模块。
- M2/M3 可在 M1 后并行：认证与本地文件互不依赖。
- M4 依赖 M3 的本地文件能力与 M2 的登录态。
- M5 依赖 M3 本地文件；发布依赖 M4。
- M6 依赖 M2 登录态（可匿名浏览）与共享类型/契约。
- M7 依赖 M6 阅读页与 M2 登录态。
- M8 依赖 M2 用户会话与 M7 评论/评审数据。
- M9 可较晚实现，不阻塞核心写作/阅读。
- M10 放在最后统一质量。

## 5. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 旧代码细节丢失 | 保留旧项目副本/行为快照；必要时从旧代码迁入行为规则 |
| API 无文档 | 以 `api-research.md` 与 `api.config.example.json` 为准，adapter 隔离 |
| 从零项目范围失控 | 每个里程碑只做本文件任务，新功能先登记到 `decisions.md` |
| 多平台差异 | 每个里程碑至少跑 `dev`/`build`；M10 统一打包验证 |
| 无自动化测试 | M10 前补 domain/adapter 单测与关键流程回归 |
